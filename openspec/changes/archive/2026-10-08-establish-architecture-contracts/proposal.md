# Proposal

## Why

NightHawk's Plan.md Phase 1 ("Establish architecture, contracts, and
compatibility") is partially complete: `docs/01-architecture.md` /
`02-configuration.md` / `03-diagrams.md`, the platform/tenant/network schemas,
the typed Python renderer, and the AWS object-storage Terraform facade are
implemented and locally tested. Two foundation gaps block every later phase:
there is no SOPS + age secret lifecycle workflow (the configuration contract
only validates secret *references*, never materializes or rotates them), and
`config/versions.yaml` pins only Mimir, Tempo, Pyroscope, SeaweedFS, Terraform,
and the AWS provider — it omits k3s, Cilium, MetalLB, Longhorn, Traefik,
cert-manager, Strimzi/Kafka, Helm chart versions, SOPS, age, and a tested OS
distribution/architecture matrix. Without these, Ansible host automation,
Kubernetes delivery, and production secret handling (Phases 2, 5, and 6) have
no verified, pinned contract to build against.

## What Changes

- Add a SOPS + age secret lifecycle workflow: generation of age key pairs,
  encryption of new/updated secrets under `secrets/`, decryption into a
  git-ignored, restricted-permission runtime materialization directory with
  explicit cleanup, and rotation of an existing secret's value without
  changing its reference. Production requires operator-provided age
  recipients; local/dev flows may generate their own throwaway recipients.
- Add a prerequisite/doctor check that verifies required local tooling (SOPS,
  age, Python/pip pins) is present, is a pinned/supported version, and fails
  explicitly and actionably otherwise — before any workflow command runs.
- Extend `config/versions.yaml` (and, where the tool supports it, a lockfile
  or checksum list alongside it) with pinned, source-verified versions for
  k3s, Cilium, MetalLB, Longhorn, Traefik, cert-manager, Strimzi/Kafka, the
  Grafana Helm charts used by the platform, SOPS, and age, plus a declared
  supported OS distribution/architecture matrix for self-hosted nodes.
- Extend the configuration contract/schema so a platform document's secret
  references can be validated against the actual encrypted files generated by
  the new secrets workflow (existence and key presence), without ever
  decrypting them during ordinary `validate`/`render-contracts` runs.
- Update `docs/01-architecture.md` and `docs/02-configuration.md` to describe
  the implemented secrets workflow and the completed compatibility matrix,
  replacing the current "separate implementation gate" / "remaining pins"
  language with accurate implemented-scope statements.

## Capabilities

### New Capabilities

- `secrets-workflow`: SOPS + age baseline automation for generating,
  encrypting, decrypting, rotating, and cleaning up tenant/gateway/storage
  secrets referenced by the platform configuration contract, plus the
  prerequisite tooling checks it depends on.
- `compatibility-matrix`: The authoritative, version-pinned, source-verified
  record of every component/tool/chart NightHawk depends on across all three
  deployment profiles, and the validation that keeps pins internally
  consistent and complete before deployment-dependent work consumes them.

### Modified Capabilities

(none — no existing `openspec/specs/` capabilities predate this change)

## Impact

- Affected code: `nighthawk/` (new secrets module, doctor/prerequisite check,
  CLI subcommands in `nighthawk/__main__.py`), `config/platform.schema.json`
  (secret-reference validation hook), `config/versions.yaml` (new pins),
  `tests/` (new unit tests for secrets lifecycle, doctor checks, and extended
  version-matrix validation).
- Affected docs: `docs/01-architecture.md`, `docs/02-configuration.md`.
- New runtime artifacts: a git-ignored `secrets/` directory convention for
  encrypted files and a git-ignored, restricted-permission materialization
  directory for decrypted runtime secrets (neither committed).
- Dependencies: adds SOPS and age as required local/CI tooling (version-pinned
  in `config/versions.yaml`); no new Python package dependencies are expected
  beyond what `requirements.txt` already provides, pending implementation
  review.
- No changes to Docker Compose, Ansible, Kubernetes/Helm, or AWS deployment
  artifacts in this change — those remain later-phase work that will consume
  this foundation.
