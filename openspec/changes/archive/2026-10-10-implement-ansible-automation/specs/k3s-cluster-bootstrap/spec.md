# Spec Delta

## Purpose

Turns prepared Ubuntu machines into the Kubernetes cluster the self-hosted
profile runs on: k3s servers and agents with the cluster network installed,
in a shape that has been checked to be possible before anything is changed.

## ADDED Requirements

### Requirement: Verified k3s installation
The system SHALL install the k3s version the compatibility matrix pins from a
binary whose checksum matches the matrix, without running a remote install
script, and SHALL disable the bundled network plugin, ingress controller,
and service load balancer.

#### Scenario: Installing a server
- **WHEN** the first server is bootstrapped
- **THEN** the pinned version is running with the bundled network plugin,
  ingress controller, and service load balancer disabled

#### Scenario: Checksum mismatch
- **WHEN** the downloaded binary's checksum differs from the matrix
- **THEN** nothing is installed and the role fails naming the artifact

#### Scenario: Another version running
- **WHEN** a node already runs a different k3s version
- **THEN** the role fails and states both versions, unless the operator
  explicitly asked for the change

### Requirement: Join token generated once and kept in Vault
The cluster join token SHALL be generated by the command-line tool, stored
only in Vault under a secret reference the platform document declares, and
never replaced once it exists. It SHALL reach nodes only as a copied file.

#### Scenario: First bootstrap
- **WHEN** a cluster is bootstrapped and no token exists
- **THEN** a token is generated, stored in Vault, and used by every node

#### Scenario: Later runs
- **WHEN** the playbook is run again or a node is added
- **THEN** the existing token is used and Vault is not written to

#### Scenario: Token in output
- **WHEN** a bootstrap or join runs with verbose output
- **THEN** the token does not appear

### Requirement: Joining servers and agents
The system SHALL join further servers and agents to the first server, one
server at a time, and SHALL report success only when every node is
registered and Ready.

#### Scenario: Adding an agent
- **WHEN** an agent is added to the inventory and the playbook is run
- **THEN** the agent joins, and existing nodes are not restarted

#### Scenario: Node not Ready
- **WHEN** a node does not become Ready within the stated time
- **THEN** the playbook fails and names the node

### Requirement: Cluster network installed with the cluster
The system SHALL install the pinned Cilium release as part of the bootstrap,
so that nodes become Ready, configured for the pod and service address
ranges and the MTU the inventory declares.

#### Scenario: Nodes become Ready
- **WHEN** the bootstrap completes
- **THEN** every node is Ready and the cluster network's own status reports
  healthy

#### Scenario: Other add-ons
- **WHEN** the bootstrap completes
- **THEN** no load balancer, storage, ingress, or certificate controller has
  been installed by it

### Requirement: Development and production shapes
The inventory SHALL state whether the cluster is a single-node development
cluster or a multi-node production cluster. The production shape SHALL
require an odd number of at least three servers and at least three nodes
that offer storage.

#### Scenario: Single-node development cluster
- **WHEN** the development shape is declared with one node
- **THEN** that node is bootstrapped as server and workload node

#### Scenario: Production with too few servers
- **WHEN** the production shape is declared with fewer than three servers or
  an even number
- **THEN** the preflight fails before changing any host

#### Scenario: Development shape with several nodes
- **WHEN** the development shape is declared with more than one node
- **THEN** the preflight fails and says which shape to declare

### Requirement: Prerequisite preflight
Before changing any host, the bootstrap SHALL verify what the cluster
network and the later storage and load-balancer add-ons need, and SHALL
reject a layout that cannot work: the kernel version and modules, the
packages the storage add-on needs, a declared storage disk on each storage
node that exists and is not in use, one MTU across all nodes, pod and
service ranges that do not overlap the node network, and a load-balancer
address pool that is non-empty, lies in the node network, and contains no
node address.

#### Scenario: Layout that can work
- **WHEN** every prerequisite holds on every node
- **THEN** the bootstrap proceeds

#### Scenario: Several problems
- **WHEN** more than one prerequisite fails across the nodes
- **THEN** the preflight reports all of them, by node, and changes nothing

#### Scenario: Address pool overlaps a node
- **WHEN** the load-balancer address pool contains a node's address
- **THEN** the preflight fails and names the address

#### Scenario: Storage disk missing or in use
- **WHEN** a storage node's declared disk does not exist or holds a mounted
  filesystem
- **THEN** the preflight fails and names the node and disk

#### Scenario: Mismatched MTU
- **WHEN** nodes' cluster-facing interfaces have different MTUs
- **THEN** the preflight fails and lists each node's value

### Requirement: Cluster credentials stay protected
The administrative kubeconfig SHALL remain readable only by root on the
servers, and SHALL be copied to the control machine only when the operator
asks, to a file readable only by its owner.

#### Scenario: After bootstrap
- **WHEN** the bootstrap completes without a request for the kubeconfig
- **THEN** no cluster credential has left the servers

#### Scenario: Fetching the kubeconfig
- **WHEN** the operator asks for the kubeconfig
- **THEN** it is written on the control machine with owner-only permissions,
  addressed to a reachable server
